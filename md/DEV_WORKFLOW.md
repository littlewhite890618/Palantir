# 開發流程：何時該開需求規格文件

這份文件記錄「什麼狀況該先開一份需求規格文件討論、什麼狀況可以直接動手改」的判斷標準，以及文件該如何隨需求迭代更新。

## 核心測試

聽完需求後，是「馬上能動手」，還是「腦中冒出兩三種做法，需要先問使用者選哪個」？

- 前者 → **執行型**，直接做，不用開文件。
- 後者 → **設計型**，先討論，值得留文件。

## 執行型（小範圍）

目標明確、只有一種合理做法，沒有需要抉擇的分岔點。

例：
- 修一個明確原因的 bug
- 加一個連結、調整一個樣式
- 把重複的 UI 元件抽成共用元件（做法只有複製貼上抽出來一種）

→ 不用開文件，直接討論、直接改。

## 設計型（大範圍）

存在需要抉擇的分岔點：存哪裡、要不要做、格式怎麼定，答案不只一種、需要取捨。

例：
- 「補助案要能收藏」——要決定存 localStorage 還是後端資料庫、要不要跨裝置同步
- 要不要導入 TypeScript
- gov_subsidy 專案裡「怎麼讓申請須知抓取更穩定」——每個機關網站結構不同，需要試錯調整

→ 先討論，等**初步需求定案後**才把結論寫入需求規格文件。文件記的是討論收斂出的結論，不是討論過程中的草稿——不邊聊邊寫，定案後才落地。

## 邊界情況：執行型中途升級

原本看似執行型的任務，過程中冒出分岔點，就要中途升級為設計型。

例：修 bug「搜尋結果排序不對」，查下去發現是前後端欄位命名不一致的結構性問題（改前端配合、還是改後端統一格式？）——這時停下來討論、定案後才寫文件，不要硬著頭皮先選一個做法改下去。

## 文件如何迭代

需求之後再變動，**更新同一份文件**，不重新開新檔案。文件是活的，跟著需求版本走；下次接續討論時，先讀這份文件而不是重新解釋一次需求。
