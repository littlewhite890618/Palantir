## Purpose

定義搜尋器 topbar 通知鈴鐺的行為契約：未讀筆數怎麼算、已讀怎麼判斷與存放、popover 顯示什麼、點擊後導向哪裡，以及這個入口只在本機開發模式存在的限制。實際的新案清單內容不在這個能力範圍內，屬於下一個能力（N2）。

## ADDED Requirements

### Requirement: 資料來源不可用時不顯示鈴鐺

通知鈴鐺 SHALL 只在能取得已審核通過資料的環境（前端設定了本機 API 位址）顯示；取不到資料來源時，topbar MUST NOT 顯示鈴鐺，也 MUST NOT 對任何端點發出請求或顯示錯誤訊息。

此功能規劃未來要在正式發布版本提供給一般使用者，因此程式碼允許被打包進正式產物；本需求約束的是「顯示與否」，不是「打包與否」——這點與管理台（僅供內部使用、必須整段排除）不同。

#### Scenario: 沒有資料來源時不顯示鈴鐺

- **WHEN** 使用者開啟未設定本機 API 位址的版本（例如目前的正式發布站）
- **THEN** topbar 沒有通知鈴鐺，畫面上沒有任何通知相關元素，也不會因為取不到資料而顯示錯誤

#### Scenario: 有資料來源時顯示鈴鐺

- **WHEN** 使用者以本機開發模式開啟前端
- **THEN** topbar 出現通知鈴鐺圖示

### Requirement: 未讀筆數只計入經審核通過的案子

鈴鐺的未讀數字 SHALL 只計入透過管理台審核流程通過（`subsidies_pending.status = approved`）的案子，且其 `reviewed_at` 晚於使用者「上次已讀時間」；MUST NOT 計入未經審核流程、直接寫入正式表的既有資料。

#### Scenario: 舊匯入資料不計入

- **WHEN** 正式表裡有一批資料是在通知功能存在之前、繞過審核流程直接匯入的
- **THEN** 這批資料 MUST NOT 被算進未讀數字，不論使用者上次已讀時間是何時

#### Scenario: 新審核通過的案子計入未讀

- **WHEN** 使用者上次已讀時間之後，管理員在審核頁又通過了 3 筆案子
- **THEN** 鈴鐺未讀數字顯示 3

### Requirement: 已讀狀態存於本機瀏覽器，不寫入資料庫

使用者點開通知鈴鐺時，系統 SHALL 把當下時間記錄為「上次已讀時間」並存於使用者瀏覽器本機（不透過任何 API 寫入資料庫）；已讀狀態 SHALL 只影響該瀏覽器自身之後的未讀筆數計算，MUST NOT 影響其他瀏覽器或裝置看到的未讀數字。

#### Scenario: 點開鈴鐺後未讀數字歸零

- **WHEN** 使用者點開通知鈴鐺，此時有 3 筆未讀
- **THEN** popover 顯示「新增了 3 筆補助案」，鈴鐺徽章隨即消失或歸零

#### Scenario: 已讀狀態不影響其他裝置

- **WHEN** 使用者在自己的電腦點開鈴鐺標記已讀
- **THEN** 另一台電腦開啟同一個本機開發環境時，未讀數字不受影響，依該裝置自己記錄的已讀時間計算

#### Scenario: 下次造訪只計算新增部分

- **WHEN** 使用者已讀過一次、之後管理員又審核通過 2 筆新案子
- **THEN** 鈴鐺未讀數字顯示 2，不包含已讀過的那些筆數

### Requirement: popover 顯示新增筆數

點擊通知鈴鐺 SHALL 開啟一個 popover，顯示「新增了 X 筆補助案」，X 為未讀筆數；未讀數為 0 時 SHALL 顯示沒有新案的訊息，而非空白或錯誤。

#### Scenario: 有未讀案件時顯示筆數

- **WHEN** 未讀數字為 3
- **THEN** popover 顯示「新增了 3 筆補助案」

#### Scenario: 沒有未讀案件時的提示

- **WHEN** 未讀數字為 0
- **THEN** popover 顯示「目前沒有新增的補助案」一類的訊息，不顯示「新增了 0 筆補助案」

### Requirement: 可點擊導向新案列表入口

popover 中顯示筆數的文字 SHALL 可點擊，點擊後導向新案列表頁面的路徑；在該頁面完成清單功能（後續能力）之前，此路徑 SHALL 顯示「功能開發中」之類的占位內容，而非錯誤頁面或空白頁。

#### Scenario: 清單頁尚未完成時顯示占位內容

- **WHEN** 使用者點擊 popover 中的筆數文字，且新案列表功能尚未完成
- **THEN** 頁面顯示「功能開發中」的提示，不顯示 404 或空白畫面
